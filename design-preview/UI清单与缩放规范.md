# TickNote 完整界面设计与布局约束

主界面风格已获用户认可。当前阶段补齐全部界面与状态，以现有 .NET 8 / WinForms 为实现边界。用户允许按需使用第三方控件，但要求保持轻量。当前尚未添加第三方 C# UI 库，也未修改现有 C# 业务代码。

## 一、界面覆盖

完整交互源文件为 `ticknote-complete.html`，浏览器预览为 `complete.html`。预览上方“查看界面”目录可以逐项打开以下设计。

## 二、保持既有功能语义

- 提醒倒计时仅作建议，“刚活动完”、跳过和推迟均可直接操作。倒计时归零不自动关窗、不自动保存。
- 在提醒里选择待办只带入内容和标签，不完成或改写待办。
- 今日工作流水在每次提醒中默认隐藏，用户主动展开后才显示。
- “保存记录”独立于活动结束按钮，保存成功反馈与空内容反馈都有设计。
- 临时收起提醒会保留草稿，关闭临时窗口也应返回提醒。
- 编辑关联工作记录时，同步内容与标签；日期、时间只作用于当前记录。
- 编辑待办保留原来的所属日期和完成状态。
- 报告同期间重复保存提供覆盖最新、保留两份、取消三个选择。
- 迁移新目录与接管已有数据使用不同的确认文案。

## 三、缩放与布局原则

HTML 是视觉与交互参考。浏览器的宽度检查不能替代 WinForms 高 DPI 验收，也不能把 CSS 像素直接照抄为物理像素。

### 统一度量与缩放归属

- 字体、间距和基础尺寸以 96 DPI 逻辑单位描述。正文沿用 Microsoft YaHei UI 约 9–10pt；字号不会因空间不足而自动缩小。
- 常用间距采用 8 / 12 / 16 / 24 的逻辑单位，主要按钮最小高度约 32；实际高度以字体的首选尺寸为下限。
- 延续当前 DpiForm 的单一手动缩放入口。MainForm、WorkspacePage、弹窗和独立 OverlayForm 必须分别明确谁负责缩放，避免混用自动缩放和手动 Scale。
- 顶层窗口 Bounds、字体、最小尺寸的 DPI 处理与子控件缩放只各执行一次。主窗口创建后才添加的页面尤其需要检查。
- 按当前 DeviceDpi 从逻辑单位计算尺寸，不通过持续乘旧尺寸叠加缩放。切回原 DPI 后，不应留下逐次累积的尺寸误差。
- 响应宽度的阈值用逻辑宽度比较；不能把物理 ClientSize 与 96 DPI 阈值直接比较。

### 界面伸缩规则

| 界面 | 横向规则 | 纵向与小屏规则 |
| --- | --- | --- |
| 主窗口 | 延续约 760×500 的常规最小尺寸；导航宽度按逻辑单位定义，内容列占剩余宽度 | 页眉、状态栏保留；页面内容可滚动；工作区不足时实际屏幕可用区域优先 |
| 表单 | 标签按内容测量，输入列占剩余空间；双列装不下时改为单列 | 多行正文伸缩；底部操作区单独占行，不被正文推到窗口外 |
| 搜索与筛选 | 搜索框弹性伸缩；日期与操作按钮按首选尺寸测量；不足时整组换行 | 换行后重新计算容器高度，禁止仍使用换行前的固定高度 |
| 待办和流水列表 | 元数据列保留必要宽度，内容列占剩余空间且不出现负宽度 | 列表自身滚动，长内容有全文预览；勾选框和行高随字体测量 |
| 报告 | 左侧归档列表与正文编辑区分配剩余宽度；窄预览中可上下排列 | 编辑区滚动；保存、复制等操作单独保留在底部 |
| 到时提醒 | 常规卡片约 620–660 逻辑宽；上限为当前显示器可用宽度减外边距 | 标题、输入、标签、记录区按内容排布；卡片高度上限取工作区；低高度时中部滚动，主要活动按钮保留可见 |
| 提醒今日记录 | 每条内容换行，操作按钮允许另起一行 | 展开记录区设定合理高度上限并滚动，不能无限撑大整张卡片 |
| 临时收起窗口 | 常规约 460–490 逻辑宽；三个按钮按内容测量，必要时折行 | 草稿区伸缩、只读滚动，返回按钮始终可见 |
| 选择、编辑窗口 | 约 520–760 逻辑宽，输入区占剩余空间，长标签可编辑 | 列表/正文滚动，确认/取消保持独立按钮行 |
| 记录日历 | 7 列等宽；月份与翻页按钮按内容测量 | 单元格不能压小到文字相互覆盖，不依赖写死坐标 |
| 设置 | 使用 5 个标签页，标签和说明可换行；长路径按单词边界或字符换行 | 每页内容可滚动，保存与还原按钮位于页签内容区之外 |
| 确认、错误提示 | 系统 MessageBox 或统一普通对话框，内容按可用宽度换行 | 根据文本决定高度；路径和错误详情可多行显示，按钮不覆盖正文 |

若系统工作区小于常规 MinimumSize，应调整该次可用尺寸限制并启用滚动，不能让 MinimumSize 强行把窗口撑到屏幕外。

### 实施时使用的原生布局能力

优先使用 TableLayoutPanel、FlowLayoutPanel、Dock、Anchor、AutoSize、GetPreferredSize 和系统标准对话框。控件创建完后统一测量与布局，避免在 Layout 事件里反复修改会再次触发布局的尺寸，造成抖动或越来越高。

HTML 中的圆角、图标与边框只表达层级。实施时优先使用现有平面按钮、Panel、Label 和静态图标/Windows 图标字体。

### 第三方控件的使用边界

- 原生优先，确实能降低实现和维护成本、改善交互时，允许引用一个与现有 WinForms 兼容的控件库。
- AntdUI 可作为候选：其官方说明采用 GDI 绘制，支持 .NET 8，参见 https://github.com/AntdUI/AntdUI 。本次仅调研，尚未接入。
- 使用 NuGet 运行库，不把对方的 Demo、脚手架或整个项目复制进当前应用；也不假定“只用一个控件就只发布这个控件”，实际以发布产物为准。
- 不为这次外观改造增加浏览器内核、WebView2、Electron 或新的 UI 技术栈。
- 同一套颜色、字体、间距和窗口行为由应用统一管理，避免多个控件库混搭造成风格与缩放策略不一致。
- 实施试点时比较当前版本、原生改造版、候选控件版的发布大小、冷启动耗时、托盘空闲内存、打开界面后的内存和多屏 DPI 行为。未测量前不承诺具体体积和性能收益。
- 若候选控件与现有手动 DPI 策略冲突，或没有足够可见收益，则保留原生方案。

## 四、WinForms 实施阶段的验收清单

本节是后续 C# 改造的验收要求，当前尚未执行真实 WinForms 高 DPI 验收。

1. 分别在 100%、125%、150%、175%、200% 缩放下启动所有页面和窗口；250% 用于极端小工作区兜底检查。
2. 在 100% 与 150% / 200% 的两个显示器之间拖动主窗口和普通弹窗；提醒卡片检查各自屏幕的布局与同步。
3. 执行 100% → 150% → 200% → 100% 往返多次，检查是否重复缩放、累计变大/变小、字体重复处理。
4. 检查 1366×768@150%、1920×1080@200% 等低逻辑高度场景，扣除任务栏后仍能看见底部主要操作。
5. 在 100% DPI 下另测系统“文本大小”提高后的效果，不能只测显示缩放。
6. 调整到最小窗口、最大化、恢复、关闭收起后重开；切页后页面、草稿和筛选保持原行为。
7. 用长标题、30 字标签、300 字路径、多段正文、单段长英文、空列表和大量列表内容核对换行与滚动。
8. 保证没有文字截断、控件重叠、负宽度、横向溢出、按钮在窗口外、Tab 焦点不可达、DPI 改变后布局持续抖动等情况。
9. 对有意义的布局约束扩展现有回归检查；截图仍须在实际 WinForms 窗口中核对，不能只依赖程序化断言。
